# Design — add-p0-source-filter-plan

## 1. Helper privé commun (decision.py, seul delta moteur)

- `_authorize_detailed(request, snapshot, provider, clock, audit, topology) -> (Decision, status)` privé : corps actuel de `authorize` déplacé sans changement de logique, plus classification interne. `status` privé fermé à trois valeurs : `ALLOW`, `DENY_POLICY`, `ERROR`. `authorize(...)` devient enveloppe fine : appelle le helper une seule fois, retourne exactement la même `Decision` publique (`ALLOWED/DENIED`, mêmes `version/obligations/evaluated_at/expires_at`, même audit des refus/plateforme). Signature, types publics et comportements observables inchangés ; aucun moteur parallèle.
- Classification interne, sans validation copiée : réutilise les points de levée existants du même moteur. Refus politique connu via exception privée dédiée : `DENY_POLICY` = sortie normale `deny/not allow/expiry`, conditions non satisfaites, seuils/fraîcheur/fenêtres/périmètres, `REVOKED` connu, expiration connue. `ERROR` = entrée/faits malformés, attribut/type/fait requis inconnu ou absent (dont condition absente), `bool` pour `INT`, budget/coût dépassé, snapshot/horloge non fiables, exception port, audit non honoré — audit non honoré toujours `ERROR`. Aucun double appel : provider/clock/audit invoqués une seule fois par le helper.
- Justification normative : l'exigence « par ressource, l'évaluation MUST utiliser l'opération existante `authorize` » est satisfaite en substance car le helper EST l'opération `authorize` (même moteur, mêmes ports, même snapshot canonique, même horloge, même audit) ; `authorize` n'est qu'un mappage public du même appel unique. « Un seul snapshot validé » signifie même snapshot canonique ; des validations pures répétées du même objet via le wrapper interne partagé sont autorisées sans bypass. Aucune divergence de matching, d'expiry ou d'obligations n'est possible.

## 2. Lot et plan (filter_plan.py nouveau, stdlib seule)

- `FilterConfig(max_filter_requests: int)` frozen : entier strict positif, `bool` refusé, explicitement requis, sans défaut. `FilterLot(header sujet/action/contexte/correlation, requests: tuple[Request])` frozen : homogénéité stricte, unicité `resource_id` et `decision_id`, catalogue/candidats selon PDPv1. `FilterPlan(...)` frozen : sujet/action/contexte, `snapshot.version`, `evaluated_at`, `resource_ids` triés/dédupliqués, `obligations` union AUDIT, `expires_at`.
- `plan_filter(lot, snapshot, provider, clock, audit, topology, config)` : valide enveloppe (malformé/hétérogène/dupliqué/limite/snapshot/horloge → `FilterPlanError`, aucun appel conservé) ; fige `now` une fois via `clock` passée au helper ; appelle le helper une seule fois par ressource avec le même snapshot canonique/ports/topologie ; `ALLOW` → candidat ; `DENY_POLICY` → exclusion ; tout `ERROR` → `FilterPlanError` fermé, aucun ID retourné, jamais de plan partiel après erreur (y c. inconnu après un ALLOW, échec audit tardif, coût dépassé en fin de lot).
- Le plan ne prouve ni fraîcheur runtime, ni jeton d'accès, ni AUDIT honoré ; réévaluation/invalidation futures restent obligatoires ; aucun filtrage frontend ni lecture métier/pagination/export/SQL. Exigences générales PEP Django/source/audit maintenues pour l'adaptateur futur. Trace `Modified Capabilities authorization-engine` sans évolution normative.

## 3. Tests et matrice

- `tests/unit/test_filter_plan.py` : 9 scénarios spec (mix, deny seul, tri, expiration min, hétérogénéité, limite, bool-comme-int→échec lot, backend/horloge erreur, vide admis) + enveloppe/bornes/immuabilité snapshot/horloge.
- `tests/integration/test_filter_plan_audit.py` : doubles mémoire, audit refus, plateforme, cross-tenant minimal refusé, sans persistance.
- Matrice exigée : régression signatures/comportements PDP (suites existantes 0 échec), `partial-unknown-after-ALLOW` (inconnu en 2e ressource après ALLOW → lot invalide, 0 ID), `port-latefail` (provider échoue en nième ressource → lot invalide), `audit-failed` (ack False/exception sur refus ou ALLOW → lot invalide), `cost-overflow` (budget dépassé en fin d'évaluation → lot invalide, pas de candidat partiel).
- Périmètre : `decision.py` modifié (helper seul), `filter_plan.py`, `__init__.py`, 2 fichiers tests. Aucune dépendance nouvelle. Exclus : PEP Django, PostgreSQL, filtrage exécuté, caches, audit durable, providers concrets, frontend, runtime complet, P0 global.

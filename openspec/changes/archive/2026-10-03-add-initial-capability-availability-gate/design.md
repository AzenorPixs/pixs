# Conception du gate de disponibilité des capacités

## Context

La spec `capabilities` comporte quatre exigences ; R2 exige le graphe DECLARED → RESOLVED → AVAILABLE avec DEGRADED, DISABLED et BLOCKED, une capacité obligatoire non AVAILABLE bloquant l'activation et une optionnelle isolée avec repli déclaré. TECHNICAL 7.1 distingue RESOLVED (contrat, provider et dépendances déterminés) d'AVAILABLE (capacité utilisable) : une liaison résolue ou une conformité passée ne prouve pas une opérabilité courante. Le chemin lifecycle réel existe (`hooks.py` : pré-contrôle fermé puis exécution ordonnée des callbacks fournis par l'hôte sur HOOK_POINTS install/enable/configure/start) ; la désactivation déclarative existe côté backend (`RuntimeProfile.disabled_capabilities`). Le schéma manifest 1 ne porte le repli que du côté offre : le repli consommateur est une entrée hôte explicite, pas un champ manifest. Aucun README kernel n'existe ; la docstring du module suffit (pas de README gratuite).

## Goals / Non-Goals

But : gate effectif des six états de disponibilité, attaché au chemin lifecycle réel avant callbacks activation/start, alimenté exclusivement par déclarations opérationnelles explicites de l'hôte ; déterministe, pur, sans IO. Non-buts : fabrication d'AVAILABLE depuis provider_ref ou conformité seuls, seconde résolution, parsing de diagnostics, modification de composition.py/hooks.py/state.py/manifest/semver, fanion, registre, probe/Django/PG dans le noyau, norme nouvelle, scénario ajouté, disponibilité opérationnelle de production, P0 global.

## Decisions

- Types exacts (`@dataclass(frozen=True)`, tous champs sans défaut) :
  - `CapabilityObservation` : `capability_id` (identifiant nu validé par `parse_requirement` : cible sans contraintes), `capability_version` (SemVer 2.0.0 complète via `parse_version`), `provider_id` (identifiant nu), `operable` (exactement bool — opérabilité courante explicite, provenance hôte).
  - `CapabilityFallback` : `capability_id` (identifiant nu), `fallback` (chaîne non vide — repli consommateur déclaré par configuration hôte validée ; séparé de la criticité et du repli d'offre `ProvidedCapability`, jamais réutilisé).
  - `CapabilityState` : `capability_id`, `capability_version` (str ou None), `provider_id` (str ou None), `state` — un enregistrement par descripteur.
  - `ConsumedCapabilityState` : `consumer_id`, `capability_id`, `provider_id` (str ou None), `capability_version` (str ou None), `state`, `fallback` (str ou None).
  - `GatedLifecycleResult` : `calls` (tuple de `HookCall`), `capability_states` (tuple), `consumed_states` (tuple), `diagnostics` (tuple FATAL), `warnings` (tuple NONFATAL — champ obligatoire).
- API exacte (pur, stdlib, sans IO ; importe `CompositionResult`, `ComponentManifest`, `Diagnostic`, `parse_requirement`, `parse_version`, `run_hooks`, `HookCall`) :
  - `compute_capability_availability(composition, manifests, observations, optional_fallbacks=(), disabled_capabilities=()) -> tuple[tuple[CapabilityState, ...], tuple[ConsumedCapabilityState, ...], tuple[Diagnostic, ...], tuple[Diagnostic, ...]]` — les deux derniers tuples sont distincts : diagnostics FATAUX et warnings NONFATAUX.
  - `run_gated_hooks(composition, manifests, hooks, observations, optional_fallbacks=(), disabled_capabilities=()) -> GatedLifecycleResult`
- Séparation FATAL/NONFATAL : un diagnostic FATAL (cohérence, déclaration manquante, required non AVAILABLE) refuse tout effet ; un warning NONFATAL (isolation DEGRADED d'une OPTIONAL) n'empêche pas l'exécution : règle du wrapper — diagnostics fatals vides ET warnings seuls → `run_hooks` appelé réellement ; diagnostics fatals non vides → zéro `HookCall`, aucun appel à `run_hooks`. Les états calculés (`capability_states`, `consumed_states`) restent restitués en présence de diagnostics fatals lorsque la classification fermée demeure possible ; ils ne sont vides que sur une entrée malformée interdisant toute classification — aucune perte automatique de tous les états valides au moindre FATAL, et un warning OPTIONAL accompagné d'un FATAL required reste un warning même sans callback.
- Validation fermée en une seule passe, précédence avant toute itération/hash/égalité sur contenus : contrôles de types exacts par identité `type(x) est Classe` — jamais `type(x) in (…)` (l'appartenance à un tuple déclencherait le hook `__eq__` de la métaclasse) ; aucune destructuration par défaut ne masque un type faux : les valeurs par défaut `()` sont des entrées de plein droit validées comme les autres.
- Précédence des six états par capacité :
  1. `DISABLED` — `capability_id` figurant dans `disabled_capabilities` (provenance : RuntimeProfile validé côté hôte ; le kernel n'importe jamais le backend).
  2. `AVAILABLE` — descripteur lié (`provider_ref` non None) ET observation appariée au triple exact (`capability_id`, `capability_version`, `provider_ref`) ET `operable` True ET non DISABLED.
  3. `BLOCKED` — descripteur lié AVEC observation appariée ET `operable` False : opérabilité déclarée explicitement fausse (état explicite, jamais DISABLED) ; consommation REQUIRED → FATAL, OPTIONAL → selon repli.
  4. `RESOLVED` — descripteur lié sans observation appariée : opérabilité NON attestée ; la liaison (`provider_ref` non None) est un fait résolu réel, jamais déduite « non consommé ».
  5. `DECLARED` — descripteur fourni avec `provider_ref` None : aucun binding résolu (jamais déduit automatiquement « non consommé »).
  6. États de consommation, PROJETÉS des faits résolus du consommateur : `AVAILABLE` (fait résolu propre au consommateur + observation `operable` True appariée au triple) ; `DEGRADED` — consommation OPTIONAL non AVAILABLE (zéro fait compatible après projection — cas normal d'absence/incompatibilité déjà toléré par compose, observation `operable` False, DISABLED) AVEC `CapabilityFallback` apparié : isolée + warning NONFATAL, composant reste valide ; `BLOCKED` — consommation REQUIRED non AVAILABLE (zéro fait compatible après projection avec `activated is True`, plusieurs faits compatibles — ambiguïté, observation manquante/incohérente/`operable` False, DISABLED) : diagnostic FATAL, zéro callback.
- Faits de précondition et PROJECTION des faits déjà résolus, sans seconde résolution ni parsing de diagnostics : le gate consomme le `CompositionResult` figé — exigences : `type(x) is CompositionResult`, `activated is True`, `stage == "activated"`, `diagnostics == ()` (résolution et conformité déjà réussies par compose). Les exigences consommateur sont lues déclarativement dans les manifests validés (`dependency_capabilities` / `optional_dependency_capabilities`), l'identité de cible extraite par `parse_requirement` (le parseur partagé) sans évaluer de contrainte comme résolution ni consulter des candidats non liés ; la contrainte déclarée du consommateur est conservée telle quelle. L'association consommateur→fournisseur est une PROJECTION des faits déjà résolus, en trois filtres successifs : (i) descripteurs LIÉS uniquement (`provider_ref` non None, jamais de candidat non lié), filtrés sur `capability_id` égal à l'identité de cible de l'exigence — les arêtes et observations d'autres cibles (autres capacités, contrats, composants) sont ignorées ; (ii) le fournisseur du descripteur lié est associé au consommateur par une arête `(consumer_id, provider_id)` de `composition.edges` — les arêtes ne sont PAS typées par capacité : elles ne servent qu'à associer ce couple, jamais à classifier la capacité et une arête multiple pour d'autres cibles n'est jamais un refus ; (iii) la `capability_version` exacte déclarée par le descripteur lié est vérifiée par `matches()` contre l'entrée du consommateur (évaluateur partagé — vérifier la compatibilité sur des faits déjà résolus n'est PAS une nouvelle résolution). Seul APRÈS filtrage, le nombre de faits compatibles fonde l'association : consommation REQUIRED avec `activated is True` — zéro fait compatible = cohérence FATALE (BLOCKED), plus d'un fait compatible = cohérence FATALE d'ambiguïté pour tous (jamais un choix arbitraire, n'implique pas de nouvelles candidatures) ; consommation OPTIONAL — zéro fait compatible est le CAS NORMAL d'absence/incompatibilité déjà toléré par compose (`activated is True`) : avec `CapabilityFallback` déclaré → DEGRADED + warning NONFATAL, sans fallback déclaré → FATAL de déclaration manquante. Le mode fournisseur configuré est déjà reflété dans les faits liés (`provider_ref` non None) ; aucun candidat non lié n'est jamais consulté. Aucun texte de diagnostic n'est jamais re-parsé et aucun binding n'est inventé.
- Cohérence d'identité : chaque observation DOIT correspondre exactement à un descripteur de `composition.capability_descriptors` (`capability_id`, `capability_version`, `provider_ref` égaux) ; observation non appariée → refus avant effet (jamais un appariement par capability_id seul : plusieurs fournisseurs ou versions d'une même capacité produisent des descripteurs distincts). Une observation n'associe JAMAIS un consommateur à un fournisseur : l'association provient exclusivement du fait résolu propre au consommateur (arête + descripteur lié + `matches()`) ; une observation AVAILABLE du fournisseur d'un autre consommateur n'autorise jamais l'exigence REQUIRED d'un autre consommateur.
- Déclarations manquantes refusées avant tout effet : consommation REQUIRED sans fait résolu cohérent, sans observation appariée `operable` True, ou désactivée → FATAL ; `CapabilityFallback` est exigé SEULEMENT pour une consommation OPTIONAL non AVAILABLE — une OPTIONAL AVAILABLE sans fallback déclaré passe (aucune obligation normative nouvelle) ; `CapabilityFallback` en double sur le même `capability_id` → refus (ambiguïté) ; la map GLOBALE `capability_id` → fallback est partagée, déclarée par l'hôte, validée, restituée dans `ConsumedCapabilityState.fallback` et expliquée dans le résultat (un mapping spécifique `(consumer_id, capability_id)` reste une option design ultérieure sans API supplémentaire maintenant) ; `disabled_capabilities` : chaînes non vides identifiants nus, doublons refusés.
- Wrapper : `run_gated_hooks` type et valide les entrées (conteneurs et clés de `hooks` compris) AVANT toute comparaison et projection, puis valide gate et projection : diagnostic FATAL → `GatedLifecycleResult` avec `calls=()` avant tout effet et AVANT tout appel à `run_hooks`, tout en restituant les états VALIDES calculés (`capability_states`, `consumed_states`, y compris le `BLOCKED` d'une required non AVAILABLE ou d'une refus d'opérabilité) et les warnings NONFATAUX d'OPTIONAL même sans callback ; les états ne sont vides que lorsqu'une entrée malformée interdit toute classification fermée — aucune perte automatique de tous les états valides au moindre FATAL ; warnings seuls → appel RÉEL de `run_hooks(composition.order, hooks)` autorisé. La validation interne de `run_hooks` refuse avant toute exécution ; ses diagnostics (fatals) sont fusionnés tels quels. Limite explicite conservée depuis `hooks.py` : un callback hôte effectif peut lever une exception propagée par `run_hooks` après un possible effet partiel — le noyau n'isole pas l'effet de l'hôte, n'émet aucun diagnostic d'exécution et ne prétend aucun rollback ; la garantie « aucun hook partiel » ne couvre que le refus de prévalidation/gate, jamais l'exécution des callbacks. Contrat de types de `hooks` : conteneurs et clés exacts contrôlés par le gate AVANT toute comparaison, projection et arbitrage (entrée potentiellement malveillante) ; la validation de `run_hooks` reste exécutée à l'ancien point, avant tout callback ; la garantie zéro appel couvre la prévalidation du gate et celle de `run_hooks`, jamais un rollback d'exception hôte (déjà acquitté). Le contrôle de qualité appelable reste celui de `run_hooks`, appliqué aux callbacks effectifs, sans jamais invoquer un hook étranger (`__iter__`, `__bool__`, `__repr__`, `__str__`, `__eq__`, `__hash__`) d'un objet invalide. `hooks.py` et `state.py` restent bornés et inchangés ; l'ancienne API publique est préservée (compatibilité documentée par les docstrings P0).
- Refus sans écho : diagnostics d'étape `validate`, élément `lifecycle.availability.*`, nommant composant, capacité ou fournisseur validé et règle violée, jamais de valeur brute.

## Validation

Strict OpenSpec avant code puis après preuves ; tests unitaires (six états et précédence, séparation FATAL/warnings, refus fermés avant effet, cohérence d'identité, PROJECTION des faits résolus : deux consommateurs/même capacité/contraintes disjointes, observation AVAILABLE du mauvais fournisseur jamais autorisante, arête absente/multiple/hors contrainte refusée sans choix arbitraire, BLOCKED explicite `operable` False distinct de DISABLED, OPTIONAL AVAILABLE sans fallback autorisée, doublons, types exacts, déterminisme, sans écho de valeur brute) et intégration (subprocess frais via `sys.executable`, gardes IO activées causalement avant l'import, callbacks passés et comptés, preuve ZÉRO appel quand FATAL avant tout départ — jamais un rollback simulé, warnings seuls exécutant réellement `run_hooks`, permutations d'ordre d'entrée produisant des états identiques, succès puis refus par état, exception callback hôte propagée conformément à `run_hooks` avec limite hôte explicite, sans Django/PG/réseau) sous mandats distincts sur `/home/devops/python/current/bin/python3` (Python 3.14.8) ; régression ciblée des suites lifecycle/descripteurs/composition existantes ; vérificateur hashé ensuite ; cochage/archive/STATISTIQUES distincts.

## Risks / Trade-offs

Le delta MODIFIED reprend R2 mot à mot sans norme nouvelle ni scénario ajouté : la validation stricte doit confirmer l'acceptation d'un MODIFIED sans changement de texte ; tout écart est rapporté à CGPT avant toute écriture. Le gate n'atteste qu'une opérabilité déclarée par l'hôte au point d'exécution du chemin lifecycle : aucune disponibilité opérationnelle de production n'est prétendue, et un état d'AVAILABLE ne survit pas à l'absence d'observation. Le gate émet ses propres refus nommant le constat sans dupliquer les textes de résolution ; toute redondance de diagnostic observée serait rapportée sans correction silencieuse.
